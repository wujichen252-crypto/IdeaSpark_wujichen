# IdeaSpark 开源生态集成方案（嵌入式 · 团队协作闭环）

> 版本：v1.0 ｜ 状态：待评审
> 核心决策：初期采用**嵌入式整合**（npm 组件直接引入），不做独立 tool 模块；
> 目标是以最少的外部依赖，把现有自研能力串成**团队协作闭环**，形成自己的生态。

---

## 一、方案定位与原则

### 1.1 我们要做的是什么

不是"工具合集"，而是**一条完整的团队协作任务流**：

> 团队从"一个想法"出发，在平台内完成 发散 → 结构化 → 任务分解 → 协同创作 → 交付，
> 全程不离开 IdeaSpark，所有产物沉淀为项目资产，可被 AI 读取和再加工。

### 1.2 四条铁律（选型与集成的判断标准）

| 原则 | 说明 |
|------|------|
| **许可证安全** | 只引入 MIT / Apache-2.0 / BSD；AGPL、GPL、自定义许可（tldraw、Planka 等）一律排除或仅独立部署 |
| **数据可控** | 每个工具的产物必须能导出为 JSON 存入我们自己的 files 体系，成为"项目资产"，而非锁在第三方格式里 |
| **协议统一** | 所有嵌入编辑器必须遵守统一的接入协议（见第六节），新增一个编辑器的成本 ≤ 1 天 |
| **闭环优先** | 只补"任务流缺口"，不重复造已有能力；能不自研就不自研，能不引入就不引入 |

## 二、现状盘点（自有资产）

| 资产 | 位置 | 闭环中的角色 |
|------|------|--------------|
| 在线 Excel 编辑器 | `views/editor/ExcelEditorView.vue` | 协同创作 · 数据 |
| 在线 PPT 编辑器 | `views/editor/SlideEditorView.vue` | 协同创作 · 演示交付 |
| Markdown 文档编辑器 + AI 面板 | `views/editor/AiDocumentEditorView.vue` + `components/markdown/` | 协同创作 · 文档 |
| 项目管理 / 看板 / 工作台 | `views/project/`、`views/workbench/` | 任务分解与分配 |
| 团队 / 成员协作 | `apps/teams`、`WorkbenchTeamView` | 组织与权限 |
| AI 引擎（DeepSeek） | `apps/ai` | 全流程编排者 |
| 文件体系（OSS） | `apps/files` | 所有产物的统一存储 |
| 社区 | `apps/community` | 成果外溢与发现 |

**结论：创作与交付环节已齐备，缺的是"前半段"（头脑风暴、结构化）和"胶水"（实时协同）。**

## 三、闭环设计：团队任务流 × 工具位

```
想法 → ① 头脑风暴 → ② 需求梳理 → ③ 流程设计 → ④ 任务分解 → ⑤ 协同创作 → ⑥ 评审交付
        [白板]       [思维导图]     [流程图]      [看板/项目]     [文档/表格/PPT]    [分享/导出]
        新增          新增           新增          已有           已有(+协同升级)     已有
```

- ①②③ 是本次嵌入引入的**新工具位**（补齐前半段）
- ⑤ 的升级靠 **Yjs 协同底座**（把"各写各的"变成"一起写"）
- 所有节点产物统一落库到 files 体系 → AI 可跨节点编排（如：把白板草图转成任务清单、根据文档生成思维导图）——**这是"生态"区别于"工具堆砌"的本质**

## 四、精选项目清单（共 5 个，宁缺毋滥）

| # | 项目 | 许可证 | 工具位 | 嵌入方式 | Vue3 兼容 | 入选理由 |
|---|------|--------|--------|----------|-----------|----------|
| 1 | **Yjs + y-websocket** | MIT | 协同底座（贯穿⑤） | npm + 独立 Node 同步服务 | 框架无关 | CRDT 事实标准，让文档/白板/导图真正多人实时协作，是闭环的灵魂 |
| 2 | **Excalidraw** | MIT | ① 白板 | `@excalidraw/excalidraw` npm（react-island 挂载） | 需 React 岛，见 6.3 | 白板第一开源项目，生态成熟，自有 JSON 场景数据可完整入库 |
| 3 | **simple-mind-map** | MIT | ② 思维导图 | npm 直接引入 | 框架无关（作者即 Vue 项目） | JSON 数据完全可控，支持多格式导出，中文文档友好 |
| 4 | **LogicFlow** | Apache-2.0 | ③ 流程图 | npm 直接引入 | 官方支持 Vue | 滴滴出品，纯 JS 内核，graphData JSON 可入库，可定制节点 |
| 5 | **Tiptap**（+ `extension-collaboration`） | MIT | ⑤ 协同文档升级 | npm 直接引入 | **官方 @tiptap/vue-3** | ProseMirror 内核 + 一等公民 Yjs 协同支持；作为现有 Markdown 编辑器的协同版升级路线（可选替换，非强制） |

### 选型说明

- **1 + 2 + 3 + 4 构成最小闭环**：白板、导图、流程图三个新工具位 + 一个协同底座，全部 MIT/Apache-2.0，全部 JSON 可控。
- **5 是第二阶段项**：现有 Markdown 编辑器能用，但天然不适合多人 CRDT 协同（文本 diff 冲突）。若要做"腾讯文档感"的协同写作，Tiptap 是 MIT 生态里的标准答案；若初期人力紧，可先只给白板/导图做协同（Yjs 直接绑定其 JSON 状态）。
- 三个新画布类工具（白板/导图/流程图）**初期不做多人实时协同，只做"单人编辑 + 版本保存 + 评论"**，协同底座先服务文档——降低初期复杂度，避免一上来就要运维 websocket 集群。

## 五、落选清单与原因（防止后续再踩坑）

| 项目 | 落选原因 | 备注 |
|------|----------|------|
| tldraw | **自定义许可证**，v4 起生产环境需密钥 + 水印，商用付费 | 技术上很好，法务上过不去 |

## 六、统一接入协议（EmbeddedEditor 契约）

所有嵌入编辑器（无论自研还是开源）遵守同一份契约，这是"以后项目不庞大、不失控"的保险。

### 6.1 前端契约：`<EmbeddedEditor>` 壳组件

新建 `components/embedded/EmbeddedEditor.vue` 作为统一外壳，职责：

```
props:
  artifactType   // 'whiteboard' | 'mindmap' | 'flow' | 'doc' | 'sheet' | 'slide'
  projectId      // 所属项目
  fileId         // 对应 files 体系中的资产 ID（可空=新建）
  readonly?: boolean

壳组件统一提供（编辑器本体不关心）：
  - Nexus 风格 Header（文件名、保存状态、返回、AI 按钮、导出）
  - 自动保存调度（防抖 + 离开页面前强制保存）
  - 主题桥接（黑白灰 nexus 变量注入，开源组件样式覆盖收敛在壳内）
  - 懒加载（defineAsyncComponent，编辑器本体按路由切分 chunk）
```

### 6.2 数据契约：统一"项目资产"

每个编辑器本体只负责两件事：**加载时拿到 JSON、变更时吐出 JSON**。

```
GET  /api/projects/{project_id}/files/{file_id}/content  → { type, schema_version, payload(JSON) }
PUT  /api/projects/{project_id}/files/{file_id}/content  ← 同上（带乐观锁版本号）
```

- 后端不新增业务表，复用现有 `apps/files`，`payload` 存 OSS，元数据存文件表
- `schema_version` 字段保证未来开源组件大版本升级时数据可迁移
- AI 模块按 `type` 读写 payload → 跨工具编排成为可能（白板→任务、文档→导图）

### 6.3 特殊嵌入项处理

- **Excalidraw（React 岛）**：在壳组件内 `createRoot()` 挂载 React 岛，仅 Excalidraw 目录引入 React 依赖，通过 `onChange` 拿 `scene` JSON、`initialData` 传入；Vite 单独分包，避免污染主 chunk。
- **y-websocket 服务**：独立 Node 进程（`collab-server/`，Docker 化），职责仅三件：房间转发、awareness 在线状态、定时把 Y.Doc 更新回写 Django 文件 API。不碰业务逻辑，挂了不影响单人编辑。

### 6.4 工具注册表（轻量，一张配置 + 一个常量）

不建独立 tool 模块，仅在 `constants/embeddedEditors.ts` 维护：

```
{ key, name, type, asyncLoader, icon, supportedExports }
```

工作台/项目页按此渲染入口。未来若真要开放第三方工具，再升级为后端注册表——**现在不提前抽象**。

## 七、分阶段实施路线

### Phase 1 · 闭环骨架（先跑通"任务流前半段"）

1. 定义 `EmbeddedEditor` 壳 + 文件 content API（6.1 / 6.2）
2. 引入 simple-mind-map（npm 直入，最快见效）→ 项目内"需求脑图"
3. 引入 LogicFlow → 项目内"流程设计"
4. 引入 Excalidraw（react-island 打样，验证分包策略）→ 项目内"白板"
5. 三个工具入口挂到项目工作区（`ProjectWorkspaceView`），产物走统一资产协议

**验收：一个想法从白板草图 → 思维导图拆解 → 流程图定型，全程在平台内完成且产物入库。**

### Phase 2 · 协同底座（把"各写各的"变成"一起写"）

1. 部署 y-websocket 协同服务（Docker，纳入 `dev.ps1` 可选启动）
2. 白板/导图/流程图接入 Yjs 共享状态（awareness 光标 + 冲突自动合并）
3. 文档协同评估：现有 Markdown 编辑器保留，新建 Tiptap 协同文档作为"团队共创文档"类型
4. 团队成员在线状态进入项目页（复用 teams 成员数据）

**验收：两个账号同时编辑同一白板/文档，实时可见、刷新不丢。**

### Phase 3 · 生态深化（AI 编排 + 按需扩展）

1. AI 跨资产编排：一句话生成导图初稿、白板转任务清单、文档转 PPT 大纲
2. 按需评估：FullCalendar 排期视图、Univer 表格升级、LiveKit 音视频
3. 工具注册表视需要升级为后端配置

## 八、风险与对策

| 风险 | 等级 | 对策 |
|------|------|------|
| React 岛导致包体膨胀 | 中 | Excalidraw 单独 lazy chunk；实测 gzip 约 1MB 级，白板页按需加载 |
| y-websocket 服务运维负担 | 中 | 服务无状态化 + 持久化走 Django API；初期仅文档类开协同，控制并发面 |
| 开源组件大版本 breaking change | 中 | `schema_version` + payload 入库（不依赖组件内部存储），锁 minor 版本升级 |
| 许可证合规疏漏 | 低 | 本方案已逐库核实 LICENSE；CI 加 license-checker 卡口（只允许 MIT/Apache-2.0/BSD） |
| 工具位膨胀、重回"tool 模块"老路 | 高 | 铁律第四条：新工具必须能说出它补了任务流哪个缺口，否则不进 |

---

## 九、总结

- **引入 5 个开源项目（全部 MIT/Apache-2.0）**：Yjs、Excalidraw、simple-mind-map、LogicFlow、Tiptap（Phase 2 可选）
- **不新建 tool 模块**：以 `EmbeddedEditor` 协议 + 统一项目资产格式嵌入现有项目工作区
- **闭环判据**：想法→发散→结构化→分解→共创→交付全程不出平台；产物皆 JSON 入库；AI 可跨节点编排
- **克制即生态**：宁缺毋滥，每个新工具都要在任务流里"有工位"，否则拒绝
