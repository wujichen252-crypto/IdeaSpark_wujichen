# IdeaSpark 项目耦合度自检报告

> 生成时间：2026-10-13 ｜ 分析脚本：`.workbuddy/analysis/coupling.py`
> 范围：frontend/src（154 个 TS/Vue 模块）+ backend/apps（9 个 Django app / 53 个 py 文件）

---

## 一、总体结论

**耦合度：中等，大方向健康，局部有明确债务。**

| 维度 | 评价 | 说明 |
|---|---|---|
| 分层方向 | ✅ 健康 | 不稳定度梯度正确：store(0.08) → api(0.32) → views(0.74)，依赖始终从易变层指向稳定层 |
| 模块间耦合 | ✅ 良好 | **视图之间零直接引用**；平均扇出 2.21，无上帝组件互相纠缠 |
| 循环依赖 | 🔴 有问题 | 前端 1 个 73 模块大环（含真实运行时循环链）+ 1 个 types 双向环 |
| 分层违规 | 🟡 少量 | 7 条实质违规（api→store ×2、constants→store ×1、constants→components ×4） |
| 后端 app 边界 | 🟡 基本清晰 | app 内分层零违规；app 间有 3 处模块级双向依赖 |
| 文件规模 | 🟡 偏大 | 前端 8 个文件 >1800 行；后端 projects/services.py 939 行 |

## 二、前端依赖分析

### 2.1 量化指标

模块总数 154，依赖边 341，平均扇出 2.21。

| 层 | 扇入(Ca) | 扇出(Ce) | 不稳定度 I=Ce/(Ca+Ce) | 评价 |
|---|---|---|---|---|
| store | 45 | 4 | **0.08** | 最稳定，正确的枢纽位置 |
| utils | 10 | 0 | 0.00 | 纯叶子，完美 |
| composables | 23 | 6 | 0.21 | 稳定 |
| api | 150 | 70 | 0.32 | 稳定（被 37 个文件共用 types.ts） |
| components | 35 | 26 | 0.43 | 合理 |
| constants | 8 | 9 | 0.53 | 偏不稳定（见违规） |
| views | 57 | 166 | 0.74 | 最易变，符合预期 |
| router | 9 | 52 | 0.85 | 易变，符合预期 |

扇入 Top5：`api/types.ts`(37)、`store/index.ts`(27)、`api/request.ts`(25)、`store/modules/aiWorkshop.ts`(16)、`api/project.ts`(14)。

### 2.2 🔴 问题 1：73 模块大环 + 一条真实运行时循环链

依赖图存在一个 **73 个模块的强连通分量**（占全部模块 47%），构成链条：

```
api/request.ts ──静态导入──> router/index.ts ──> router/modules/community.ts
      ▲                                                    │
      │                                           静态导入 CommunityView.vue
      │                                                    │
      └────────────────────────────────────────────────────┘
            （CommunityView → api/community → api/request.ts）
```

**风险评估**：其中 `request.ts → router`、`router/modules/community.ts → CommunityView`、`CommunityView → api/community` 三段都是**静态导入**，构成真实运行时循环（ESM 循环引用下存在初始化顺序依赖，HMR 和单测环境容易暴露时序 bug）。环的其余部分经由路由表的 `() => import()` 动态导入相连，运行时风险低，但静态分析上整个图粘连成一片。

另一条 2 模块环：`constants/aiModules.ts ↔ store/modules/aiWorkshop.ts`（互相 import 类型与常量）。

### 2.3 🟡 问题 2：分层违规（7 条）

| 违规 | 位置 | 性质 |
|---|---|---|
| `api → store` | `api/request.ts` 导入 `useUserStore`（401 刷新 token 用） | 常见模式，但属层级倒置 |
| `api → store` | `api/projectFile.ts` 从 `store/modules/aiWorkshop` 导入 `ProjectFile` **类型** | 类型放错了层，应移到 `api/types.ts` |
| `constants → store` | `constants/aiModules.ts` 从 store 导入 `StageChecklistItem/Artifact` 类型 | 与 2.2 的 2 模块环互为因果 |
| `constants → components` ×4 | `constants/embeddedEditors.ts` 懒加载三个编辑器组件 | **注册表模式，设计使然，可接受** |
| `router → views` ×44 | 路由表引用视图 | **设计使然，可接受** |

### 2.5 ✅ 前端做得好的地方

- **视图间零耦合**：没有任何 view 直接 import 另一个 view，页面边界干净

- `utils`（0 扇出）、`composables` 保持叶子/近叶子状态
- 类型集中于 `api/types.ts`（扇入 37），有统一类型源

## 三、后端依赖分析

### 3.1 App 间依赖矩阵

```
accounts  → projects, teams      (3 处，均为函数内延迟导入 ✅)
ai        → accounts             (auth)
community → accounts, projects   (posts.py 模块级导入 Project)
files     → accounts             (auth)
notifications → accounts         (auth)
projects  → accounts, community, teams  (teams 模块级；community 函数内)
security_logs → accounts         (auth)
teams     → accounts, projects   (services.py 模块级导入 Project)
```

**双向依赖 2 组**：`projects ↔ teams`、`projects ↔ community`。
**accounts 被 7 个 app 依赖**——作为认证枢纽合理，且均只依赖其 auth/models，无反向污染。

### 3.2 🟢 做得好的地方

- **app 内分层零违规**：无 `services → api`、无 `models → services/api` 的倒置
- **函数内延迟导入用得好**：`accounts/services.py`（3 处）、`projects/services.py:651,665` 都用函数内 `from apps.x.models import Y` 主动规避 Django app 加载环——这是正确的 Django 实践
- `common/` 包（auth/db/exceptions/middleware/pagination/response）职责清晰，被各 app 稳定复用

### 3.3 🟡 需要关注的

1. **3 处模块级跨 app model 导入**形成静态双向依赖：
   - `projects/services.py:28` → `apps.teams.models.Team`
   - `community/services/posts.py:14` → `apps.projects.models.Project`
   - `teams/services.py:10` → `apps.projects.models.Project`
2. **`projects/services.py` 939 行**（25+ 个函数混杂项目 CRUD、文件、artifact 总线、收藏、点赞），是最重的后端文件，建议按领域拆成 `project_service.py` / `file_service.py` / `artifact_service.py` / `social_service.py`

## 四、修复建议（按优先级）

### P0 — 解掉运行时循环（前端）

1. **`api/request.ts` 不再静态导入 router**（第 4 行）：401 跳转逻辑改为事件机制（如 mitt 事件总线）或由调用方注入 redirect 回调，从根上斩断 `api → router` 这条倒置边。
2. **`router/modules/community.ts:2`、`router/modules/workbench.ts:2`** 两处静态视图导入改为 `component: () => import(...)`，与其余 44 条路由保持一致。

### P1 — 消除分层违规与 types 环

3. **`api/projectFile.ts`**：`ProjectFile` 类型迁至 `api/types.ts`（该文件本就是类型枢纽，扇入 37）。
4. **`constants/aiModules.ts ↔ store/modules/aiWorkshop.ts`**：共享类型（`StageChecklistItem/Artifact/ProjectModule/ModuleData`）上移到 `api/types.ts` 或新建 `src/types/`，constants 与 store 共同依赖它，环即消解。

### P2 — 控制文件规模

5. `ProjectFileEditorView.vue`（81% 脚本）优先拆分为 composable + 子组件；`SlideEditorView` 次之。
6. 后端 `projects/services.py` 按领域拆分为多个 service 模块。
7. 四个 AI composable（`useDocAi/useExcelAi/useMdAi/useSlideAi`）提取公共基座，止住复制粘贴。

### P3 — 后端双向依赖（可选，当前风险低）

8. 若后续加事件/信号机制（Django signals 或领域事件），可将 `projects ↔ teams/community` 的模块级 model 导入改为事件订阅；当前函数内延迟导入已足够安全，可不动。

## 五、结论

项目耦合度**中等且可控**：分层方向、模块边界、视图隔离都做得对，后端 Django 侧的延迟导入实践甚至优于多数同类项目。真正的债务集中在两点——**前端 `request.ts ↔ router` 静态环**（唯一有运行时风险的循环，改动量约 10 行）和**一批上帝文件**（重构量较大但无正确性风险）。建议按 P0 → P1 顺序处理，一小时内可消除全部循环依赖与分层违规。
